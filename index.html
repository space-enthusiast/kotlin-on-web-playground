GraalVM Web Image · 설명서

Kotlin 컴파일러를 통째로 브라우저에 넣는 법

서버 없이, 독자의 브라우저 탭 안에서 진짜 kotlinc가 코드를 컴파일하고 실행한다. 어떻게 가능한지 그림으로 정리했다.

한 줄 요약. kotlinc는 원래 JVM에서만 도는 자바 프로그램이다. Web Image는 이 프로그램을 내 컴퓨터에서 미리 브라우저가 알아듣는 WebAssembly(.wasm)로 통째로 번역해 둔다. 그러면 독자의 브라우저는 JVM 없이 그 파일을 받아 바로 실행할 수 있다.

비유: 통역사냐, 번역서냐

브라우저는 JVM 바이트코드(.class)를 못 읽는다. 해결 방법은 크게 세 가지다.

평소의 JVM

현장 통역사

실행할 때마다 JVM이 바이트코드를 그 자리에서 해석한다. 브라우저에는 이 통역사가 없다.

CheerpJ · WebVM

통역사를 데려가기

JVM(또는 리눅스 전체)을 브라우저 안에서 흉내 낸다. 되긴 하지만 무겁고 느리다.

GraalVM Web Image

미리 번역해 출판

빌드할 때 한 번 번역해 .wasm으로 만들어 둔다. 독자는 번역본만 받으면 된다.

"미리 번역"을 전문 용어로 AOT(Ahead-Of-Time) 컴파일이라고 한다. 평소 JVM은 실행 중에 번역하는 JIT(Just-In-Time) 방식이다.

전체 흐름

두 장소에서 일이 일어난다. 색으로 구분했다: 주황 = 내 컴퓨터, 빌드할 때 한 번 · 청록 = 독자 브라우저, Run 누를 때마다.

① 빌드 시점 · 내 컴퓨터 · 한 번만
kotlin-compiler.jarkotlinc 본체. 자바 바이트코드 묶음
→
native-image --tool:svm-wasmOracle GraalVM 25.1+. 아래 4단계를 수행
→
kotlinc.wasm + kotlinc.js약 75MB 번역본 + 작은 JS 포장지
↓ 블로그(정적 파일 호스팅)에 올림 ↓
② 실행 시점 · 독자 브라우저 · Run 누를 때마다
독자가 쓴 코드binomial(2, 0.5)[1] 같은 것
→
Worker A: kotlinc.wasmstdlib.klib + 내 라이브러리.klib 와 함께 컴파일
→
program.wasm독자 코드의 결과물
→
Worker B: 실행출력 0.5를 페이지에 표시

헷갈리기 쉬운 점: Wasm이 두 번 나온다.

① kotlinc 자체를 Wasm으로 만든 건 GraalVM Web Image가 한 일이다.
② 독자 코드를 Wasm으로 만드는 건 그 안에서 돌아가는 Kotlin 컴파일러의 Wasm 백엔드(Kotlin/Wasm)가 하는 일이다.
서로 다른 두 도구가 각자 Wasm을 만든다. Worker는 화면을 멈추지 않게 뒤에서 일하는 별도 스레드다.

번역기 안에서 일어나는 4단계

native-image가 .jar를 .wasm으로 바꿀 때 하는 일이다.

1

쓰이는 코드만 골라내기 (도달성 분석)

main에서 출발해 "실행될 수 있는" 메서드와 클래스만 따라가며 표시한다. 한 번도 닿지 않는 코드는 버린다.

대가: 닫힌 세계(closed world). 실행 중에 새 클래스를 불러오는 일이 불가능하다. 리플렉션처럼 "이름으로 나중에 찾는" 코드는 빌드 전에 목록(메타데이터)으로 알려줘야 한다. kotlinc 같은 큰 프로그램에서 이게 제일 손이 많이 가는 부분이다.

2

시작 상태를 미리 찍어두기 (이미지 힙)

프로그램이 켜질 때 만드는 초기 객체 일부를 빌드 중에 미리 만들어 결과물 안에 사진처럼 저장한다.

효과: 브라우저에서 켜질 때 준비 작업이 줄어 빨리 시작한다.

3

Wasm 코드 생성 (WasmGC 사용)

남은 메서드를 WebAssembly 명령으로 번역한다. 자바 객체는 WasmGC 객체로 바꾼다. 즉 메모리 정리(가비지 컬렉션)를 브라우저가 대신 해준다. JVM의 GC를 통째로 싣고 갈 필요가 없다.

그래서 WasmGC·예외 처리를 지원하는 최신 브라우저가 필요하다. 2024년 말부터 주요 브라우저 모두 지원한다. 마지막에 Binaryen의 wasm-as가 텍스트를 바이너리 .wasm으로 조립한다.

4

JS 포장지 붙이기

Wasm은 혼자서는 콘솔 출력도, 파일 읽기도 못 한다. 그런 바깥일은 함께 생성되는 .js가 연결해 준다.

그래서 .wasm 단독으로는 못 돌린다. 반드시 JS 런타임(브라우저나 Node.js)이 같이 있어야 한다.

실제 숫자 (wasm-code-editor 기준)

  • 다운로드: 컴파일러 약 75 MB + 표준 라이브러리 12 MB. 페이지 열 때가 아니라 첫 Run 때 받고, 이후엔 브라우저 캐시.
  • 첫 컴파일 약 5초, 그 다음부터 약 1초.
  • 빌드에 필요: Oracle GraalVM 25.1+, Binaryen 119+. 독자는 아무것도 설치하지 않는다.

내 수학 블로그에 쓰려면

남은 빈칸은 하나다. 그 프로젝트는 아직 표준 라이브러리만 붙여서 컴파일한다. 내 라이브러리도 stdlib과 같은 형태(Wasm용 .klib)로 빌드해 컴파일러에 함께 넘기면 될 것으로 보이지만, 아직 누가 해본 기록은 없다.

1

wasm-code-editor를 Oracle GraalVM으로 빌드해 println("hello")가 브라우저에서 도는지 확인.

2

binomPmf 하나만 든 작은 라이브러리를 Wasm .klib으로 빌드.

3

브라우저 안 컴파일러가 그 .klib을 받아 binomPmf(1, 2, 0.5) → 0.5를 출력하면 성공.

빌드·배포 전에 라이선스도 확인할 것: 해당 레포는 라이선스 표기가 없고, Oracle GraalVM은 자체 약관이 있다.

용어 정리

JVM
자바 가상 머신. 바이트코드를 실행하는 프로그램. kotlinc도 여기서 돈다.
바이트코드
.class 파일 안의 중간 언어. JVM만 읽을 수 있다.
AOT / JIT
미리 번역 / 실행하면서 번역.
WebAssembly
브라우저가 직접 실행하는 저수준 바이너리 형식. .wasm.
WasmGC
Wasm에 추가된 기능. 객체 메모리 정리를 브라우저가 맡는다.
klib
Kotlin 라이브러리 파일 형식. Wasm/JS/Native 타깃용 라이브러리가 이 형태다.
Web Worker
페이지와 별도로 뒤에서 도는 스레드. 무거운 컴파일 중에도 화면이 멈추지 않는다.
Binaryen
Wasm 도구 모음. Web Image가 마지막 조립에 쓴다.
